# 通り芯/中心線の昇格・降格・削除（昇格/降格/削除問題）の既知の限界と受容方針

## 方針（2026-09-25 ユーザー裁定）
昇格・降格・削除（および通り芯の移動・追加を含む中心線操作全般）には、包括的なルールと制限が今後必要。それまでの間、以後の処理でこれに絡む問題が見つかった場合は既知の限界として受容し、都度の場当たり的な特例を積み増さない。新たに見つかった限界は本ファイルに追記する。ただし削除は2026-09-27の「CL削除＝境界」（D案。下記「採った設計の記録」参照）で境界化し、新たな限界を残さない方針へ切り替えた——本節の「既知の限界として受容する」対象は昇格・降格・移動（および削除以外の中心線操作全般）に限られる。

## 既知の限界一覧
1. **S造の境界寄り通り芯の降格→昇格で偏心・軒の出が別値に収束する**（経路依存）: 境界寄りの通り芯を一時的に取り除くと、外周モデル基準の柱芯オフセット・軒の出量の再計算が異なる収束先に落ちる。往復しても元の値には戻らない。欠落・重複ではなく計算結果の経路依存性。
2. **通り芯・中心線の移動で他階・下階由来の孤児梁芯が残る**（**段階(g)で「undo後に他階へ残る分」は解消**。2026-09-26）: 壁由来梁芯の追従は依然として自階のみのため、**操作直後**に他階へ残る孤児梁芯自体は解消しない（後続段階「他階の梁芯追従」の候補として受容）。undo/redoでは箱（`floorRecords`）が他階のIDBバイトを操作前後の状態へ戻す・進めるため、孤児は基準の状態（操作前なら無し・操作直後の状態なら操作直後のまま）へ正しく同期する。
3. **中心線削除・移動で他平面（屋根含む）の孤児梁芯が残る**（**段階(g)で「undo後に他階へ残る分」は解消**。上記2と同じ扱い）: 「CL操作の後始末は当該階のみ」の裁定の範囲は操作直後についてのみ残る。
4. **CL操作起因の他階への構造反映はundo対象外**→**CL操作については解消（段階(g)・2026-09-26）**: `transform/centerLineOps.js`のCL操作（追加・移動・削除・偏芯・昇格・降格）が起動した構造同期の他階書込みは、起動元エントリの箱（`floorRecords`）へ記録され、そのエントリのundo/redoで一緒に戻る・やり直せる（`.claude/undo-redo.md`「構造同期の他階書込みは起動元エントリの箱へ」参照）。**残る限界**: (a) 実行中に複数の要求が合流した場合は最新エントリの箱にまとめる扱いを許容する（裁定3）。(b) 操作前の状態自体が未収束（読込み直後・`MAX_REFLECT_PASSES`で打ち切られた状態）なら、undoで戻る先もその未収束状態のまま。(c) 逆関数型エントリ（`commitCLMoveOp`の移動・`addCenterLineFromDialog`の追加）は自階の構造変化自体を記録しない——自階はbake/mergeの逆操作で戻るため元々対象外。モード境界（仕上げ脱出・構造脱出・構造突入・履歴復帰の他階反映）経由の構造反映は引き続き完全にundo対象外のまま（裁定1・別ステップ。この4番の解消はCL操作だけの範囲）——階操作（`withFloorOpUndo`）は元々全採用フロアのbefore/afterバイト列比較＋Planeメタ比較で1エントリに記録済みのため対象外に含まれない（QA指摘m-1・2026-09-26。誤記を訂正）。
5. **ダイアログ経由の中心線→通り芯（昇格）は他階の同座標重複チェックを通らない**→**解消（線種変更の移籍一本化・2026-09-30）**: ダイアログの昇格・単体追加・スパン配列とも他の平面の同座標チェックを通るようにし、削除して作り直す経路自体を廃止した。詳細は下の「採った設計の記録」参照。
6. **他階保存→同期peekの順序はIDBトランザクション順序に依存**（実機未確認。readwriteの後に作られたreadonlyは完了を待つ仕様に依存）。
7. **S造/RC造の撤去段は手動柱・基礎も撤去しうる**→**解消（手動追加材サイレント撤去回避・2026-09-30）**: 手動追加した柱・基礎・柱脚・梁は主構造を問わず`dimensionStatus:'locked'`で固定し、撤去段の既存保護条件（非`auto`）で守る。固定梁と重なる自動梁の扱い、CL削除・降格で固定材が巻き込まれるときの確認は下の「採った設計の記録」参照。**残る限界**: 保存済みの既存データの手動材（`auto`のまま）は救済しない（裁定5）。在来木造の壁線方式では固定梁の下の自動梁を撤去しない（案A・別タスク）。
8. **通り芯追加のundoは自階の依存部材しか撤去しない**: 追加からundoまでの間に他階でその通り芯を参照する壁を作図していた場合、その壁は次の`peek`で黙って消える（稀）。
9. **CL偏芯確定時の壁由来梁芯の追従は自階のみ**（段階(e)・2026-09-26）: 連動先（階段・吹抜けの他階）・在来木造の上階の壁由来梁芯は、偏芯確定で下地帯中心が動いても追従しない（**操作直後**の限界として残る——上記2と同じ扱い。段階(g)で「undoで他階へ残る分」は解消済み）。
10. **開口由来梁芯（規則O）の他階孤児は上記2・3・9と同列に受容**（S造梁芯選定ステップ6・2026-09-28）: 壁由来梁芯の追従は自階のみのため、開口由来梁芯も他階へは追従しない。
11. **中心線移動の同期経路は階段由来の開口の梁芯を追従できない**（同上）: `commitCLMoveOp`の同期経路は`belowGraph`を持てず、下階に到達元の階段がある開口辺（`source:'stairBeyond'|'stairVoid'`）の梁芯は移動に追従せず、次の再計算の現況照合（`reconcileOpeningBeamAxes`）で撤去→再生成される（id変化を受容）。
12. **偏芯したRC下地壁の辺では壁芯梁芯と開口由来梁芯が2本立ちうる**（同上）→**梁幅/2までの偏芯は解消（吹抜け小梁の共通仕様・2026-10-08）**: 梁あり判定の許容`coverTol`＝max(0.5, 梁幅/2)で辺座標・逃げ後座標のどちらに近い壁芯梁芯も「梁あり」になる。それを超える偏芯では従来どおり2本立ちうる。
13. **中心線を通り芯へ重ねる移動のundoで開口由来梁芯のidが変わる**（吹抜け小梁の共通仕様・2026-10-08）: 通り芯上の辺は「梁あり」で源にならないため、確定時の追従（`mapOpeningSourceMoves`）に乗らず、確定直後の構造同期の照合で旧梁芯が撤去される（参照切れは残らない）。undo後の再計算で同じ座標に作り直されるが別idになる（11番と同じ受容）。

14. **天井芯（S8a・2026-10-10）の限界**: (a) 天井芯の削除・他の線との併合で天井セルが併合されると、天井 key の区画は解けず部屋の CH に戻る（受容。S5 と同じ）。(b) 天井芯が中心線を越えて動いたときの矩形は読む側で min/max に正規化するのみ（越えないよう移動範囲は障害物で止めるが、逆向き＝平面で中心線を動かすときは天井芯を障害物にしない）。(c) 階固有の線で他階へ複写・昇格降格の対象にしない（`CONVERT_SUBJECT_KINDS`・`CROSS_FLOOR_COUNTERPART_KINDS` に入れない）。(d) 前方互換なし: 天井芯を持たない旧版で開くと discipline `'ceiling'` は中心線に落ちる。(e) 同座標の天井芯は展開図・切断の同座標探索から除外する（`findRunCLAt`・`switchbackCuts`の midCL。除外しないと中心線と同座標の天井芯を掴んで面の端が偏芯分ずれる）。(f) 天井芯の端部参照（extentLoRef/HiRef）は中心線の結合を止めない（裁定 2026-10-10。天井芯は平面で見えないため）——`hasExternalCenterLineReferences(id,{ignoreCeilingOnly:true})`で数えず、`absorbCenterLine`が結合で消えるピースを参照する天井芯の参照を残るピース（同軸・同座標）へ付け替える（座標不変・undo/redoで往復）。(g) 天井芯の移動確定（S8b）は中心線と同じ共通経路（`commitCLMoveOp`）で、同軸・隣接する天井芯と結合すると吸われた側の id が消え、その id を含む天井セルの区画は部屋の CH に戻る（受容。(a) と同じ。undo で戻る）。

## 採った設計の記録
- **CL削除＝境界（D案。ユーザー裁定2026-09-26〜27）**: 意匠CLの削除を仕上げモード境界（突入/脱出）と同格の「境界」とし、削除直後・同じundoエントリで部屋再解釈→エッジ同期→壁再生成→構造同期まで行う（案B。平面モードでの削除直後に部屋が併合・拡張されることも承認済み）。再解釈不能な退化ケース（対辺2本同時喪失等）だけ削除自体を拒否する（案C）。ルール1（自階の後始末＋壁再生成の明示化）・ルール2（他階への同じ後始末の伝播。屋根専用平面はdetachのみ）・ルール3（フットプリント境界＝外壁線を担うCLはどの階でも境界でなくなるまで削除拒否）・ルール4（復元不能セルの検出拒否＋削除前後差分の安全網）の4本で構成する。詳細は`.claude/structural-model.md`「起動点」節ルール2・`.claude/data-model.md`参照。
- **undo復帰時のアーキ壁ドリフトは真因を解消（2026-09-29）**: 「13.stqで通り芯削除→undo→redoすると構造材は一致するが壁の幾何だけずれる」（2026-09-25記録。probeは壁を合否から外し「注意」表示にしていた）は、壁ではなく壁が参照する子CL（通り芯に`refId`で追従する階固有の中心線）の値がずれていた。真因は2層——引き金は旧`reparentChildCenterLines`が通り芯を階グラフでしか探さずno-opになり宙に浮いた`refId`がスナップショットに残ったこと（f235719で是正）、根本は`CenterLine.value`が参照解決の成否で意味を変え未解決時に`refOffset`を二重加算していたこと。根本は`value`を常に絶対座標に一本化＋復元時の未解決参照の静的化で解消し（`.claude/data-model.md`「CLの`value`は常に絶対座標」）、probeの壁幾何は合否条件へ戻した。`chamferWalls` reactionは原因ではなかった（13.stqの壁は全数`isRoomWall`で対象外）。症状が別の是正で見えなくなっても根本は残っていた——教訓は`.claude/skills/team-lessons/SKILL.md`「症状が消えたことを根本の解消と取り違える」参照。
- **不採用: 降格をはさむ案**（通り芯→中心→補助→消去の段階降格）: 階層の最下位「補助」もセル分割・構造に参加しない種別であり、中心→補助は仕上げ側から見ると削除と同義——段階を挟んでも部屋・境界の壊れ方は変わらない上、降格ガードが削除を塞ぐ・段階ごとの降格が他階へ新idの中心線を量産する・undo3段の矛盾が新たに生じる。
- **不採用: 「外壁に絡む意匠CLは階削除で単一階まで縮小しないと削除不可」案**: 釣り合いが取れない（外壁1本のために他階の部屋・壁・建具・仕上げ・構造を全部捨てる＝複数階では外壁CLが永久に削除不可と同義）・単一階にしても最外郭の再解釈不能は残る・通り芯は全階へdetach伝播するため上下階の食い違いは元々起きない・階削除の経路は既にある、という理由で見送り、代わりにルール3（フットプリント境界ガード）を採用した。
- 通り芯削除＝全階でその通り芯を軸にする壁を消す（detachを undo 付きで他階へ伝播）。「降格してから削除」案は取り下げ（他階の壁が残る意味変更・降格ガードの持ち込み・undo合成が要るため）。
- 通り芯追加のundoは削除と同型——自階の依存部材（柱・梁・基礎）を撤去する（裁定(a)）。
- 降格直後に生成される壁由来梁芯は、昇格時に自階・他階とも吸収する（保護条件は孤児梁芯の道連れ削除と同じ述語`isProtectedWallBeamAxis`を共有）。
- S造/RC造の格子生成（`autoFillColumns`/`autoFillBeams`/`autoFillFootings`等）に、候補キー集合に無いauto部材を撤去する段を一般則として追加した（在来木造の撤去ループと同型）。
- **壁由来梁芯の追従先に既存の梁芯・通り芯がある場合は、保護されなければ旧梁芯を吸収して撤去する一般則にした**（案B・ユーザー裁定・2026-09-26。旧: 重複ガードでskipし旧梁芯を孤児として残す案A——偏芯の解除などで追従先に既存の梁芯（下階の壁が根拠に作り直されたもの）や通り芯があると孤児が残る限界があったが、この一般則で解消した）。保護条件は道連れ削除・昇格時の梁芯吸収と共通の`isProtectedWallBeamAxis`を共有する。
- **手動追加材サイレント撤去回避（ユーザー裁定2026-09-29〜30。旧限界7番「S造/RC造の撤去段は手動柱・基礎も撤去しうる」を解消）**: 手動追加した柱・基礎・柱脚・梁を`dimensionStatus:'locked'`で固定し（由来フィールドの新設は採らない）、撤去段の既存保護条件（非`auto`）にそのまま乗せて解決した。固定梁と同軸・同roleで区間が重なる自動梁は生成しない＋既存分は撤去する（S造・RC造。在来木造の壁線方式は既存の見送りのみで撤去までは広げず別タスク扱い）。CL（通り芯・梁芯・中心線）の削除・通り芯の降格で固定材が巻き込まれるときは、階ごとの本数を添えた確認を出してから削除する（中止で操作ごと取りやめ・了承でundo付きで削除）。設計意図は`.claude/structural-model.md`「手動追加は`locked`で撤去段・CL削除巻き込みから守る」節参照。
- **線種変更の移籍一本化（ユーザー裁定2026-09-29〜30。限界5番を解消）**: 種別変更（昇格・降格）を「削除して作り直す」経路と「移籍（id維持）」経路の二本立てから、移籍1本化した。あわせて「線（中心線・補助線・梁芯・通り芯）の id はプロジェクト全体で一意」を不変条件とし、複数の平面に同じ id の線を作らない設計へ変えた——検査は`app/src/lineIdUniqueness.js`（`findDuplicateLineIds`・`scanProjectLineIds`）。id の振り直し・付け替えは、参照の種類ごとに書き換え処理を書く代わりに、保存形式の中間オブジェクト（snapshot）全体を文字列の部分一致で同時置換する1関数`app/src/lineIdRemap.js remapLineIdsInSnapshot`に一本化し、事後条件「旧idが残らない」を`findLineIdOccurrences`で検査する。降格は他の平面に**新しい id**の中心線を作りその平面の通り芯id参照を一括置換（`propagateDemotedCenterLine`。旧・同id複製＝「分身」方式は廃止）、昇格は他の平面の同座標の中心線を区間・本数を問わず**吸収**する（その平面の中心線id参照を通り芯idへ一括置換し中心線を除く。`findCenterLinesToAbsorbForValues`／`applyCenterLineAbsorptionForValues`）——分身の回収（旧`recallPromotedCenterLineDuplicates`）は廃止。吸収の書込みは移籍の**後**（他平面の壁は自平面の中心線idを参照するため移籍後に読んでも壊れない。通り芯が共有グラフに入ってから書く）。既存データに同じidの線が他の平面に残っていた場合は、昇格・降格とも入口で検出し書き換えずに平面名を出して拒否する。検討案の追加・コピーは複製元のバイト列を復元する前に線（線だけ。壁・部屋等は対象外）のidを振り直す（`graphSnapshot.js serializeGraphWithFreshLineIds`）。ダイアログ経由の昇格・単体追加・スパン配列にも他の平面の同座標チェックを足し、ダイアログの昇格は削除して作り直す経路を廃止してメニューと同じ`promoteCenterToGridWithUndo`へ委譲した（確定処理は`runBusy`の関門に入る非同期処理になった）。
  - **不採用: 線の実体をプロジェクトの台帳1本へ移す案**: 効果が昇格・降格に限られ他の持ち越し課題（他階の梁芯追従等）には効かない、階のデータが「バイト列1本で自己完結」する前提（検討案コピー・undo・他階の先読み・保存ファイルが依存）を崩す、裁定「上下階の中心線は互いに無関係」（2026-09-17）と逆向きになる、という理由で見送った。再検討の条件は、線の階またぎ共有が日常の操作として必要になったとき（例: 全階共通の間仕切りを一括で動かす）。

詳細な実装は`.claude/structural-model.md`「起動点」節を参照。
