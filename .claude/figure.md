# 図面合成（Figure Composition）の設計意図

クラス・関数シグネチャは `figure/*.js` を読めば分かるため省略する。ここには横断的な設計判断のみ記す。

## なぜ図面を「階」ではなく「複数階×複数カテゴリの合成」として持つか
構造伏図は「自階の床下材＋1つ下の階の柱」のように、1枚の図面に複数階の部材が現れる（天井伏図の上階床梁・PS検討の全階重ね等も同型）。
描画対象の階とデータ帰属の階がズレるため、これを描画層・編集層にハードコードすると分岐が散る（旧 `columnGraph`/`graphForMap` 三項）。
図面を `FigureDef`（レイヤ仕様の宣言的リスト）として持ち、レンダラ・編集パネルは「どの階のどのグラフか」を `composition.graphForCategory` に委ねる。

## 3つの「階」を分離する
**帰属階**（部材データを永続化・採番する階＝floorsストアの単位）／**主題階**（その図面が何階か＝アクティブ階）／**出演階集合**（その図面に現れる供給元の階、複数可）は別物。構造伏図は出演階＝`{自階, 自階−1}` という特殊例にすぎない。

## レイヤ＝(供給階, カテゴリ, スタイル, 役割)
供給階は `figureTypes.js` の source リゾルバが解決（`'self'` と関数 source）。新トークン（`'above'`/`'allFloors'` 等）はここに追加する。表示スタイルは `figureStyle.js`（SOLID は素通し＝属性を足さない）。編集役割は `MemberListTab` が解釈（REFERENCE=閲覧可・編集不可）。

## バインディングは「自己完結した解決コンテキスト」——跨ぎ参照はしない
各レイヤのグラフは階固有CL＋通り芯参照を内包する（`peek` が階のグラフを丸ごと復元するため、中心線由来の小梁も自グラフ内で座標解決できる）。
**規律：各レイヤは自分の供給グラフ内で座標解決し、スクリーン座標を合成する。他階の部材を主題階の中心線へ再解決しない。** これにより「座標の co-register」は常に成立し、残る制限は跨ぎ参照・跨ぎ随伴（他階中心線への追従・他階からの編集）だけになる。詳細は `.claude/data-model.md`。

## 役割→編集チャネルの対応
self は通常の auto-save（FloorSwapManager のフロア auto-save）に乗る。secondaryEdit は非アクティブ階を編集可能 peek 化して下階IDBへデバウンス保存する。reference は読み取り専用。
**secondaryEdit は現状1階のみ**（`FloorSwapManager` の編集可能 peek が単一チャネルのため）。複数階同時編集が必要になった時点で FloorSwapManager 側を多チャネル化する。

## z-order はレンダラのカテゴリ固定順で決める
描画順（柱→基礎→梁→スラブ→耐力壁）はレンダラが持つ。**レイヤ宣言順には依存させない**（参照レイヤを足しても既存の重なり順が動かないようにするため）。

## レジストリと読み込み順依存（落とし穴）
各ディシプリンが自分の `FigureDef` を `registerFigure` で**モジュールロード副作用として自己登録**し、App は `getFigure(id)` で引く。
登録は当該モジュールが import されて初めて走る——App が `STRUCTURAL_FIGURE_ID` の import を失うと登録されず `getFigure` が例外になる。新図面型を足すときは「定義モジュールが必ず一度 import される」ことを担保すること。

## 拡張ポイント：新図面型は「FigureDef を1個登録」で足りる
天井伏図（上階床梁＝source:above/style:DASHED/role:REFERENCE）・PS検討（source:allFloors/style:GHOST/role:REFERENCE）等は、レンダラ・編集パネル・FigureBindingManager を改修せず定義追加だけで成立する。
例外は2つ：新しい供給階トークンが要るときは `figureTypes.js`、新しいカテゴリの**描き方**が要るときは該当レンダラ（カテゴリの描画法はレンダラ固有知識のため）。
